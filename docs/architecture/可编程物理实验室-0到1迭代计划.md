# 可编程物理实验室：0→1 迭代计划

## 实施状态

截至 2026-08-17，第一轮 **L0 + L1** 已完成首版实现：

- `/lab` 已作为独立动态入口运行，不加载现有城市页面样式；
- 新增无 UI 依赖的 `@empire/world-kernel`；
- 固定时钟支持运行、暂停、单步、倍速和重置；
- 通用 box/sphere 对象支持制造、选择和空间移动；
- 物质与能量使用权威账户结算，超额事务整体拒绝；
- Worker 输出命令事件、拒绝原因、世界状态哈希和重放报告；
- 内核确定性测试及 `/lab`、`/` 浏览器隔离回归已通过。

当前实现有意停在 L1；对象程序、效应 ABI 与执行预算仍属于下一阶段 L2。

## 1. 这张新页面要回答什么

新页面暂名 **可编程物理实验室（Programmable World Lab）**，路径为 `/lab`。

它不是现有城市页面的另一套 UI，也不是提前制作完整游戏，而是一座可以反复拆解、观察和验证世界底层机制的实验台。它必须回答四个问题：

1. 一个对象的宏观性质能否由程序定义，而不是由引擎预先枚举？
2. 对象程序能否在不绕过物质、能量、空间、时间、权限和计算约束的情况下创造开放行为？
3. 多个未知对象能否只通过通用端口与效应发生组合，形成设计者未预写的新机器？
4. AI 能否最终通过编写、测试和制造这些对象，获得真正的科学与工程创造空间？

实验页的首要产品价值是**可观察性**。每次状态变化都应能看见来源、消耗、结果以及被拒绝的原因，否则我们无法判断新设计究竟是物理世界的产物，还是代码偷偷越过了规则。

## 2. “从 0 到 1”的完成定义

这里的“1”不是完整文明，而是跑通一个最小创造闭环：

> 用户或 AI 描述一种新装置 → 生成对象程序与结构清单 → 在沙箱中编译和验证 → 使用真实库存、能量与工具制造 → 装置在世界中运行 → 所有效应经过内核结算 → 结果可以确定性重放和继承。

首个代表性场景建议使用一套内核从未听说过“名称”的组合装置：

- 能源对象持续输出能量；
- 控制对象读取温度信号；
- 执行对象把能量转化为热；
- 三者通过通用端口组成恒温加热器；
- 控制逻辑可被改写，物质与能量不能被凭空生成；
- 拔掉信号线、能源耗尽、程序死循环或越权写入时，世界给出一致且可解释的结果；
- 保存同一种子与命令序列后，重放得到相同状态哈希。

这条链路一旦成立，才说明“对象功能由代码表达、宇宙底线由内核约束”不只是概念。

## 3. 与现有城市的隔离方式

当前网页入口直接渲染单个 `App`，没有路由依赖。第一阶段不需要引入完整路由框架，可以按路径分发页面：

```text
apps/game-web/src/main.tsx
├── /      → 现有 App（城市）
└── /lab   → LabApp（可编程物理实验室）
                 ↕ 消息协议
             lab.worker.ts
                 ↕
          @empire/world-kernel
```

隔离原则：

- `/` 的现有城市模拟、Worker、协议和存档结构保持不变；
- `/lab` 使用独立 Worker、独立状态模型和独立测试；
- 世界内核放入新的无 UI 包，不把实验逻辑塞进 React 组件；
- 初期只在内存中运行，确定性重放稳定后再设计持久化格式；
- 实验成功前，不扩展现有城市的 `BuildingView`、`GameCommand` 等固定联合类型；
- 两套世界未来通过版本化快照或桥接层连接，而不是彼此直接引用内部状态。

这样可以快速试错，同时避免新宇宙模型破坏已经可运行的城市。

## 4. 页面应当长什么样

实验页不是最终玩家界面，而是“世界内核的显微镜”。建议采用五区布局：

```text
┌───────────────────────────────────────────────────────────────┐
│ 返回城市  场景/种子       运行 暂停 单步 重置  倍速  状态哈希 │
├────────────┬────────────────────────────┬─────────────────────┤
│ 场景       │                            │ 对象检查器          │
│ 设计       │       3D 实验场            │ ├ 状态与账本         │
│ 对象目录   │                            │ ├ 程序与预算         │
│ 库存/工具  │                            │ ├ 端口与连接         │
│            │                            │ └ 结构与碰撞代理     │
├────────────┴────────────────────────────┴─────────────────────┤
│ 时间线：事件 → 程序求值 → 效应提案 → 接受/拒绝 → 账本变化    │
└───────────────────────────────────────────────────────────────┘
```

交互优先级：

1. 能暂停、单步执行和恢复，而不是只能看连续动画；
2. 点击对象能追踪其物质、能量、状态、程序、端口和父子结构；
3. 每个效应标明接受或拒绝，并显示违反的约束；
4. 可以查看相同命令序列的重放哈希；
5. 到后期才加入自然语言创造入口，避免把大模型输出的偶然性误认为物理机制成立。

美术只需要清晰的几何体、颜色和连线。这个阶段追求可解释性，不追求最终城市风格。

## 5. 分阶段迭代

每一阶段都必须产生一个可操作、可验收的页面版本。下一阶段不能依赖“以后再补”的核心约束。

### L0：独立实验页壳层

**可见成果**

- `/lab` 可以独立打开；
- 有空实验场、控制栏、检查器和事件时间线占位；
- Worker 可以启动、暂停、单步和重置固定时钟；
- 能从实验页返回城市，刷新任一页面不会跳错入口。

**内核能力**

- 只有 `tick`、种子和最小消息封装；
- UI 不直接推进或修改世界状态。

**退出门槛**

- 现有 `/` 页面行为和构建结果无回归；
- 连续运行与手动单步到相同 tick 时，实验状态一致；
- Worker 生命周期不会因 React Strict Mode 重复挂载而泄漏。

### L1：确定性对象与守恒账本

**可见成果**

- 创建、选择、移动箱体和球体；
- 检查器显示对象 ID、变换、碰撞代理、物质、能量和内部状态；
- 重置并重放同一命令序列可得到相同状态哈希。

**内核能力**

- 通用 `WorldObject`，不出现房屋、黏土、炉子等领域类型；
- 权威固定步长时钟和确定性 ID；
- 物质账本、能量账本、对象所有权和基础空间占用；
- 所有变更通过命令和事务提交；
- 初始几何只支持 box、sphere 与 compound proxy。

**退出门槛**

- 无合法来源时，增加物质或能量的事务必定被拒绝；
- 100 次固定种子重放的最终哈希一致；
- UI 无法通过调试消息直接写权威状态；
- 测试覆盖创建、转移、删除、回滚和账本守恒。

### L2：对象程序与最小效应 ABI

**可见成果**

- 右侧可编辑一个对象的受限程序；
- 编译错误、运行预算和每次求值结果可见；
- 修改程序后，对象能表现出内核没有硬编码的新响应。

**内核能力**

- 第一版使用自定义确定性 DSL/字节码解释器，不直接执行任意 JavaScript；
- 程序只能读取能力句柄暴露的数据，并提交效应提案；
- 最小效应集合：
  - `SetOwnState`
  - `TransferMatter`
  - `TransferEnergy`
  - `ApplyImpulse`
  - `EmitSignal`
  - `ScheduleEvent`
- 每次求值具有指令预算、事件预算和内存预算；
- 对象的构成程序与控制程序分离：前者描述被动性质，后者必须依赖可计算的物理载体运行。

**退出门槛**

- 程序不能持有世界对象的可变引用；
- 无限循环会因预算耗尽而停止，不阻塞 Worker；
- 同一输入、代码哈希和种子必定产生相同效应提案；
- 删除一种示例装置的 UI 名称后，其程序仍能正常运行。

### L3：多对象端口与原子结算

**可见成果**

- 可视化连接能源、信号、物质等通用端口；
- 时间线展示多个对象同一 tick 的提案和统一结算结果；
- 拔线、断能、争抢同一资源时出现可解释结果。

**内核能力**

- 通用端口和能力句柄；
- 输入快照、提案收集、冲突排序、原子结算、事件派发五阶段循环；
- 转移使用预留/托管机制，防止双花；
- 拒绝原因是稳定错误码，不依赖 UI 文案；
- 对象之间不能调用“加热”“耕作”等语义 API，只能交换通用量与信号。

**退出门槛**

- 两个消费者争抢不足能量时，结果按确定规则结算；
- 事务部分失败时不产生半次转移；
- 连接顺序、对象遍历顺序不改变相同事件序列的结果；
- 权限外端口读取和写入必定被拒绝并留下记录。

### L4：结构、碰撞、力与连接

**可见成果**

- 对象会发生碰撞和冲量响应；
- 可用通用连接构造门、摆锤、推杆或黏结组合体；
- 一个信号控制的门可以完全由对象程序、端口和连接组成。

**内核能力**

- 粗粒度刚体、碰撞代理、冲量和约束连接；
- `CreateBond`、`UpdateBond`、`BreakBond`；
- 连接参数受材料库存、连接能量、工具精度和承载上限约束；
- 物体内部不需要粒子模拟，但对外的宏观力与结构失效必须统一结算。

**退出门槛**

- 内核源码中不出现“门”“胶水”“摆锤”等产品语义；
- 结构受力超过连接上限时可重复地断裂；
- 碰撞不能使系统凭空获得不受误差预算约束的能量；
- 物理步进性能和数值误差有可观测指标。

### L5：组合体、休眠与规模化

**可见成果**

- 多个对象可封装成一个可复用组合体；
- 检查器可在整体与内部组件之间展开；
- 大量静止对象不会持续消耗相同计算量。

**内核能力**

- 父子结构、外部端口映射、组合体内容哈希；
- 组合体可编译出粗粒度碰撞代理与事件路由；
- 事件驱动休眠、唤醒、局部展开和局部损伤；
- 计算成本作为世界中的受限资源和宿主运行预算分别计量。

**退出门槛**

- 10,000 个休眠对象的空闲开销保持在预设帧预算内；
- 组合体未受影响的内部对象不会被逐 tick 求值；
- 展开再折叠不改变物质、能量和连接账本；
- 局部受击只唤醒相关空间与依赖链。

> 具体帧耗时阈值应在 L0 测得目标设备基线后填写，避免现在凭空规定数字。

### L6：设计、制造与能力包络

**可见成果**

- 用户可以保存“设计”，但设计不会立即变成世界对象；
- 制造面板列出所需物质、能量、工具、精度、计算和时间；
- 同一设计在不同工具条件下可能失败、降级或产生误差。

**内核能力**

- `DesignArtifact` 只承载结构、程序、端口、清单、测试和版本；
- `ImplementationEnvelope` 描述制造者当前可实现的尺寸、精度、温度、压力、能量、计算与材料范围；
- 制造是账本事务和时间过程，不是实体反序列化；
- 已知设计可继承，能否实现仍由现实工具链决定。

**退出门槛**

- 保存或复制设计不复制物质和能量；
- 超出工具精度、库存或能源上限的制造必定失败或按显式规则降级；
- 制造中断后，已消耗资源和半成品状态可追溯；
- 设计升级具有版本与内容哈希，旧实例不会被静默改写。

### L7：AI Vibe Coding 创造闭环

**可见成果**

- 用户用自然语言描述一个装置；
- AI 生成设计清单、程序、端口声明和测试，而不是直接修改世界；
- 页面先显示沙箱测试与约束报告，用户确认后才进入制造。

**内核能力**

- 结构化设计格式与稳定编译器；
- 静态检查、属性测试、预算估算和恶意行为扫描；
- AI 输出进入与人类手写设计完全相同的验证管线；
- 模型调用结果属于提案，不属于权威事实。

**退出门槛**

- 更换模型或手写代码不会改变内核安全边界；
- AI 无法通过提示词绕过资源、权限或运行预算；
- 生成失败能定位到清单、语法、测试、能力包络或结算中的具体一层；
- 至少三个不同自然语言目标能生成行为不同但使用同一 ABI 的装置。

### L8：对抗验证、重放与可迁移存档

**可见成果**

- 提供“破坏性测试场景”：死循环、事件风暴、双花、越权写入、异常数值和结构爆炸；
- 可导出实验包，并在全新页面会话中重放；
- 时间线能定位首次状态分歧。

**内核能力**

- 内容寻址、版本化快照、命令日志和周期校验点；
- 差分重放与状态哈希树；
- 事件速率限制、对象隔离、数值边界和熔断；
- DSL/ABI/内核版本迁移声明。

**退出门槛**

- 已知攻击样例不能突破账本和权限；
- 导出/导入后最终哈希一致；
- 版本不兼容时明确拒绝，不静默产生不同世界；
- 随机属性测试能长时间运行而不出现未解释的守恒误差。

### L9：人类具身桥接实验

**可见成果**

- 实验场加入一个最小人类身体对象；
- 冷、热、能量储备、损伤与感知由物理对象和身体约束共同产生；
- 人可以借助前面创造的能源、加热器和遮蔽物改变生存状态。

**内核能力**

- 身体是受特殊权限保护的组合对象，不是跳出物理内核的角色数值表；
- 感觉是身体状态到智能体上下文的投影；
- System Prompt 决定如何理解和行动，不能取消身体的物理后果；
- 科技突破可以逐步替换或扩展身体组件，但必须经过真实制造与移植过程。

**退出门槛**

- 同一物理条件对不同人格可产生不同决策，但不会产生不同守恒结果；
- 删除“寒冷时必须找房子”这类行为脚本后，身体风险依然存在；
- 人类可以发明不同解决方案，而非只能调用预设生存动作；
- 这条链路稳定后，才设计与现有城市居民系统的桥接。

## 6. 阶段依赖关系

```mermaid
flowchart LR
    L0["L0 独立页面"] --> L1["L1 对象与账本"]
    L1 --> L2["L2 程序与效应 ABI"]
    L2 --> L3["L3 端口与结算"]
    L3 --> L4["L4 力与结构"]
    L4 --> L5["L5 组合与规模"]
    L5 --> L6["L6 设计与制造"]
    L6 --> L7["L7 AI 创造"]
    L7 --> L8["L8 对抗与重放"]
    L8 --> L9["L9 人类具身桥接"]
```

这不是说每阶段都要做成大型版本，而是强调依赖顺序：没有守恒账本，程序开放就是作弊接口；没有稳定 ABI，接入大模型只会放大返工；没有制造包络，设计会退化成“输入文字免费生成实体”。

## 7. 建议的初始代码边界

首批实现建议保持小而明确：

```text
packages/world-kernel/
├── src/types.ts
├── src/clock.ts
├── src/ledger.ts
├── src/commands.ts
├── src/settlement.ts
├── src/replay.ts
└── src/index.ts

apps/game-web/src/lab/
├── LabApp.tsx
├── LabViewport.tsx
├── LabInspector.tsx
├── LabTimeline.tsx
├── lab-worker.ts
├── lab-worker-client.ts
└── lab.css

apps/game-web/e2e/
└── programmable-world-lab.spec.ts
```

到 L2 再加入解释器，到 L6 再加入设计格式；不要提前创建一组只有名称、没有稳定职责的包。

边界规则：

- `world-kernel` 不依赖 React、Babylon 或具体游戏语义；
- Babylon 只负责显示内核快照和采集用户意图，不成为权威物理状态；
- Worker 是唯一世界推进者；
- UI 和 Worker 之间只传版本化消息；
- 测试可以在 Node 中直接运行内核，不需要浏览器才能验证守恒和重放。

## 8. 第一轮实际开发范围

建议第一轮只完成 **L0 + L1**，暂时停在“对象与账本可验证”，不要同时开始 DSL、AI 和制造。

第一轮交付应包括：

1. `/lab` 独立页面与基本五区布局；
2. 固定时钟的运行、暂停、单步、重置；
3. box/sphere 对象的创建、选择与检查；
4. 物质、能量、状态与权限的最小权威账本；
5. 命令日志、接受/拒绝原因和最终状态哈希；
6. 固定种子确定性重放；
7. 内核单元测试、Worker 集成测试和 `/` 城市回归测试。

第一轮结束时，页面还不会“发明东西”。它提供的是一块可信地基：我们能确切知道任何未来对象程序必须通过什么边界改变世界。

## 9. 暂不做的事情

- 不在 L0/L1 接入真实大模型；
- 不允许对象执行任意 JavaScript、访问 DOM、网络、系统时间或随机源；
- 不模拟原子、分子或连续场；
- 不预定义完整材料表、科技树、配方表或产品类别；
- 不复用现有城市存档格式；
- 不追求最终美术、移动端适配或玩家教学；
- 不先写“万能对象 API”，只加入当前可验证场景真正需要的最小原语；
- 不把性能优化建立在牺牲因果一致性或偷偷硬编码产品语义之上。

## 10. 何时接回现有城市

满足以下条件后，才进入城市桥接设计：

- 恒温加热器等代表性组合装置完整跑通设计、制造和运行；
- 内核能承受休眠城市对象规模；
- 重放、版本和攻击边界稳定；
- 人类身体能通过同一物理机制受益或受损；
- 实验世界不依赖实验 UI 才能运行。

届时先选择一条窄链路接入，例如“居民制造并使用一种供暖装置”，而不是一次性替换整套城市模拟。现有城市继续提供社会与视觉场景，新内核通过版本化桥接逐步接管真正需要开放创造的部分。
